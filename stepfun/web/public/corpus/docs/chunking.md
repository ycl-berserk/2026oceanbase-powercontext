# 文档分块策略

分块（chunking）决定了检索的最小单位。块太大，一个块里混着多个主题，向量被"平均"掉，召回不准；块太小，上下文被切碎，模型难以理解，而且块数变多会放大索引与检索开销。

常见做法是按语义边界切：先按段落，再按句子，累积到目标长度就断开。中文场景下"目标长度"通常取 200 到 500 字，对应嵌入模型 512 token 的输入上限。相邻块之间保留一定重叠（例如 10% 到 20%），避免关键句正好被切断在两个块之间。

重叠不是越大越好。重叠会增加存储与向量化成本，过大还会让检索结果里出现大量近似重复的块，挤占 top-K 名额。实践中 32 到 96 字的重叠足够覆盖大部分被切断的句子。

块还要带元数据：文档 ID、标题、块序号、来源路径。检索命中后前端需要展示"来自哪篇文档的第几段"，评测时也需要把块级命中映射回文档级，计算 Recall@K 与 nDCG@K。没有这些元数据，检索结果就只是一堆无法追溯的文本。

最后是切分的确定性。分块逻辑必须可复现：同样的输入、同样的参数，必须切出同样的块 ID。否则增量导入会产生重复块，评测结果也无法对齐。本项目的块 ID 采用"文档 ID + 序号"的形式，正是为了保证这一点。
